## [0.45.733] — 2026-11-05 — Fixed：v0.45.728 碎片工具二次检查——check 只认被跟踪的文件、adopt 重跑不再卡在 cherry-pick 中途、claim 转述钩子结果且推完核实失败不误报

**起因**：用户要求二次检查 v0.45.728（CHANGELOG 碎片化）有没有 bug。复核出 8 条，用户定「修确认的几条」：修了 5 条（A–E）；2 条留给用户定，1 条实测证否（见「没动」）。

### Fixed
- **A. `check` 和全量测试会为不进提交的文件变红**（`changelog_fragments.py::worktree_files`）：
  - 原来按目录扫 `changelog.d/`。开发检出在 iCloud 同步下，Finder 写的 `.DS_Store`（`.gitignore` 已忽略）和 iCloud 造的 `0.45.730 2.md` 式副本（未跟踪）都会报「文件名不合规」，可它们根本不会进提交。
  - 改为只认 git 跟踪的条目（`ls-files --cached`，含已暂存的新文件），内容取工作区（没暂存的改动照查）。口径同 `tests/_repo_files.py`。
  - 副本真被 `git add` 进来时，pre-commit 和全量测试照样红（有正对照测试）。
- **B. 完工后重跑 `adopt` 会把仓库留在 cherry-pick 中途**（`adopt`）：
  - 原来按文件内容判「已经带进来了」。完工改了标题、补了正文，内容就不同了 ⇒ 再 cherry-pick 一次 ⇒ add/add 冲突，仓库停在 cherry-pick 中途，碎片里留着冲突标记（临时仓库实测）。
  - 改为按**认领行**判：一致 ⇒「无需带入」；分支里已有同号碎片、认领行却不同 ⇒ 同一个号有两份，拒绝，不去盖它。
  - 兜底：cherry-pick 不管因为什么停在半路，都先 `git cherry-pick --abort` 撤回再报错（新函数 `_abort_cherry_pick`）。
- **C. `claim --push` 看不出守卫跑没跑**（新函数 `_report_push_guard`）：
  - 推送时捕获了输出，钩子的话整个被吞掉。真仓库上 `claim --push` 两次（0.45.729、0.45.733），终端里一行钩子输出都没有。
  - 改为转述推送输出里 `pre-push:` 开头的行。看不到放行那句（`GUARD_PASS_MARK`）⇒ 提示这个 checkout 多半没装钩子，并给出装钩子的命令。
- **D. 推送成功、之后核实时断网 ⇒ 读起来像「推送失败」**（`claim`，新函数 `_landed` / `_say_unverified`）：
  - 原来核实远端时 fetch 失败，异常直接冒出去，看不出推送其实成功了。人会重跑 claim，再占一个号，前一个变成挂着自己分支名的孤儿占位。
  - 改为按推送退出码分两种说法。退出码 0 ⇒「号多半已经占住」，给确认命令和 `adopt` 命令，写明「别直接重跑 claim」；非 0 ⇒「号大概没占住」，先看 `status` 再重跑。
  - 号已核实占住、带进当前分支时 git 出错 ⇒ 同样给 `adopt` 命令和「别重跑 claim」（原来异常直接冒出去，看不出号已经占住）。
  - 交给人的 `adopt` 命令统一由 `_adopt_cmd` 生成（带 `cd`）。
- **E. `check` 与 `render` 各写一份读取逻辑**：抽成 `_load_view`，两个命令对 `changelog.d/` 里有什么不会各说各的。这两个命令此前没有任何测试调过，现在有了。
