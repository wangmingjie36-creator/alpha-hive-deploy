## [0.45.731] — 2026-11-05 — Fixed：main CI 自 11-04 起的红——test_scan_catchup 的 UTC−5 兜底测试在 Linux 上换算 BSD date 的 -v
<!-- 认领：worktree-restart-banner-paper-cooldown 2026-11-05T09:31:44-07:00 c67df937 -->

**起因**：main 的 CI（ubuntu）自 11-04 起只红一条：`tests/test_scan_catchup.py::TestGateClockLive::test_unreadable_zone_warns_and_falls_back_to_utc_minus_5`（v0.45.714 加的）。最近一次跑完的 51276f65 是 1 failed、13762 passed。
- 这条测试在 bash 里真跑编排器补跑闸的读钟片段。时区缩写不对时，兜底那行是 `NOW_HHMM=$(date -u -v-5H +"%H%M")`。
- `-v` 是 BSD date（macOS）才有的参数。GNU date 报 `invalid option -- 'v'` ⇒ `NOW_HHMM` 为空 ⇒ 测试取 `NOW=` 时报 `AttributeError`。
- 生产只在 Mac 上跑，不受影响；本机全套一直是绿的。

### Fixed
- `tests/test_scan_catchup.py`：假 `date` 里「按 UTC 推算」那一支，改走新加的 `_UTC_DATE_SHIM`（bash 函数 `_utc_date`）。
  - 平台 date 认 `-v`（用 `date -u -v+0S` 探测）⇒ 原样调真 date。所以在 macOS 上（生产所在、本机全套）照旧验证真 BSD date 的行为。
  - 不认（GNU）⇒ 只把 `-v±N[HMS]` 换算成 `-d @epoch`，其余参数原样交给真 date。不认的参数照样报错，不猜。
  - 取不到四位 HHMM 时，断言会带上整段输出。此前报的是 `'NoneType' object has no attribute 'group'`，看不出原因。

### 为什么这么修
- **没改编排器**：它只在 macOS 上跑，`date -u -v-5H` 在那里是对的。为了 CI 往生产代码里加一条永远走不到的 GNU 分支，不值得。
- **没用 `skipif(非 darwin)`**：那样 CI 上就没人验兜底逻辑了。而这段逻辑（打 WARN、按 UTC−5 读钟）换算后在 Linux 上照样能验。

### 注意到、没改（只记录）
- 补跑闸读出的 `NOW_HHMM` 为空时（`date` 本身失败），`[ "" -lt 1630 ]` 会报 `integer expression expected`，条件为假 ⇒ **照常往下扫描**，即失败时放行。
- 生产上只有 macOS 的 `date` 本身坏掉才会走到这里。该失败放行，还是失败跳过（漏扫一天），是取舍问题，没动。
- （v0.45.735 起已改为读不到钟就不扫描：`failed_clock_unreadable` + `exit 1`，见 `changelog.d/0.45.735.md`。）

  - 修之前：复现出与 CI 完全相同的 `AttributeError`。
  - 修之后：`TestGateClockLive` 7 条全绿。
  - 不带替身（真 BSD date）也是 7 条全绿。

  - 换算 4 个（符号写反 / 小时按 60 秒算 / 丢掉其余参数 / 假 date 不接换算）：GNU 替身下红。
  - 「能力探测失效、总走换算」：macOS 上红。
