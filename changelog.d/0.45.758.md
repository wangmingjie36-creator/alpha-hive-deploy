## [0.45.758] — 2026-11-10 — 评分冻结守卫按重置机制重写：比相邻条目而非固定起点，修三处误报 + 守住「表按日期升序」；例外登记校验补正对照
<!-- 认领：claude/scoring-freeze-guard 2026-11-10T08:10:36-07:00 e933ed43 -->

v0.45.757 二次检查发现：`scoring_freeze_violations` 判「同日并入 / 更正」时只拿冻结起点 2026-11-09 比，而当前世代起点会合法地挪后。
合成数据实测三种合规操作被判违规：① 11-09 条目被更正顺延到 11-10 后，作废 0 条的改动并进 11-10；② 获批例外开出 12-01 后，
作废 0 条的改动并进 12-01；③ 那条例外自身被更正顺延到 12-02。真表末条仍是 11-09，三种都没触发过，main 上没有出错；
危害是诱导下一个会话为消红去登例外或填 `lifted`。

**为什么是重写而不是补集合**：第一版修法维护「合法起点集合」，逐种列举起点怎样挪（例外、更正）——行为对，但再出一种合法挪法
又会误报，且暗含「表按日期升序」这个没人守的前提。根因是守卫自己复刻了一份「当前起点」，而闸门的重置机制只有一条：
`cohort_start()` 取末条日期 ⇒ **条目日期比前一条大 = 开新世代、计数归零；同日 = 并入**。守卫直接对着它判。

### Fixed
- `ic_rerun_readiness.scoring_freeze_violations`：逐条与**前一条**比——日期变大且晚于冻结起点 ⇒ 开新世代，须是已登记例外，
  或是对**前一起点日**上某条目的更正（`_CORRECTS`）；同日 ⇒ 并入，放行，不管起点是怎么挪过来的。
- 同函数：条目日期早于前一条 ⇒ 直接报（表必须升序，否则末条取值让边界往回退）；**解冻不豁免**这一条。
  真表 53 条现为升序；此前 `test_cohort_start_never_moves_backwards` 只看末条，中间乱序无人报。
- 冻结声明注释、`.claude/rules/scoring-weights.md`、`experiments/scoring_freeze_queue.md`：「并进 11-09 当日」→「并进当前世代起点当日」。

### Changed
- 例外登记校验从测试体挪进 `ic_rerun_readiness.freeze_exception_problems()`（参数可注入）。此前例外表为空，校验一次都没真正执行过。

  更正只认前一起点（更正更早世代的条目仍算开新世代）；例外校验正对照（完整 / 四字段各缺一 / kind、approved、cost 格式错 / 陈旧或不需要）。
